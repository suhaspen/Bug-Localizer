# Bug Localizer — Overview

*This is the document to read right before an interview. It explains the whole
project from scratch, assuming you have not seen the code.*

---

## The problem

A user files a bug: *"Flask's `send_file` sets the wrong MIME type when the
filename has no extension."* A maintainer now has to figure out which of the
project's several hundred source files to open. On a mature codebase this is
genuinely hard, and it is the single most time-consuming step in fixing a bug —
studies of developer time consistently find that *finding* the bug takes far
longer than *fixing* it once found.

**Bug localization** is the task of automating that first step: given the text of
a bug report, rank the source files by how likely each is to contain the fault.
We are not trying to fix the bug or even to point at the exact line. We are trying
to hand a developer a list of ten files and be confident the culprit is in there.

This is a **retrieval** problem, not a generation problem. The answer already
exists in the repository; we just have to find it. That framing is what makes the
project tractable, cheap to run, and rigorously measurable.

---

## The core insight: the dataset labels itself

The obstacle to any supervised approach here is labeled data. To know whether a
ranking is good, you need ground truth: for this bug report, which files were
actually at fault? Hand-labeling that requires a domain expert per repository,
per bug. It does not scale, and it is why public bug-localization datasets are
small (a few hundred examples) and stale.

The trick this project is built on:

> **Every bug fix in git history is a labeled example, and nobody had to label it.**

When a maintainer fixes a bug, they write a commit. That commit touches a
specific set of files. Those files *are* the ground truth — not an approximation
of it, but the actual answer, written by the person who understood the bug best.
The commit message and its linked issue give us the query. Git gives us the label.
The pairing is free and it exists for every fix commit ever made.

So a single labeled example is assembled like this:

| Piece | Where it comes from |
| --- | --- |
| `query_text` — the description of the bug | The commit message (linked issue numbers are stored; fetching their bodies needs the GitHub API and is deferred — see `docs/01_dataset.md`) |
| `gold_files` — the correct answer | The non-test source files that the fix commit changed |
| The corpus to search | The repository **at the parent commit** — the last state of the code that still had the bug |
| Metadata | Repo name, fix SHA, parent SHA, timestamp |

Scale that over three active repositories and you have thousands of labeled
examples, generated by one command, on a laptop, for free.

### The rule that makes it honest

**Index the repo at the parent commit of the fix, never at the fix itself.**

This is the correctness rule the whole project hangs on, and it is worth
understanding precisely. If you indexed the repository *after* the fix, the fixed
code would be sitting in the corpus. Suppose the fix added a line
`mimetype = "application/octet-stream"` and the bug report says "wrong MIME type."
A retriever would match that line and score a bullseye — but only because it was
shown the answer. The number you would publish would be a measurement of
information leakage, not of localization skill.

Indexing at the parent commit reconstructs the exact epistemic situation the
developer was in: the buggy code, the bug description, and no knowledge of the
fix. This is called avoiding **leakage**, and it is the first thing a sharp
interviewer will probe. See `docs/glossary.md`.

The same concern shapes the query side: the query text must never quote the diff
or the fixed code. Any literal gold file path appearing in a commit message is
scrubbed before the query is stored. But the message is still written at fix
time, by someone who already knows the answer, so its vocabulary is subtly
better-informed than a real bug report's — an acknowledged compromise that makes
absolute accuracy optimistic while leaving method *comparison* valid.
`docs/01_dataset.md` treats this honestly.

## The pipeline, end to end

```
  git history                                                    metrics
      │                                                             ▲
      ▼                                                             │
  ┌────────┐    ┌──────────┐    ┌───────────┐    ┌──────────┐   ┌────────┐
  │  MINE  │───▶│  FILTER  │───▶│   INDEX   │───▶│ RETRIEVE │──▶│  EVAL  │
  └────────┘    └──────────┘    └───────────┘    └──────────┘   └────────┘
   find fix      drop noisy      corpus at        rank files     top-1/5/10
   commits       commits         parent SHA       per query      MRR, MAP
```

**1. Mine.** Walk each repository's history and pick out commits that look like
bug fixes (by commit-message convention: `BUG:`, `fixes #1234`, and similar).
Record the changed files, the parent SHA, and the timestamp.

**2. Filter.** Most commits that *look* like fixes are useless as examples, so we
discard aggressively and log exactly how many each rule removed:
- *Merge commits* — the file list is an artifact of merging, not of fixing.
- *Docs/test-only commits* — nothing to localize to; there is no source file at fault.
- *Mega-commits* (>10 files by default) — a commit touching 200 files is a refactor
  or a release. Calling all 200 files "the bug" would inflate our accuracy for free,
  since a wide net catches anything.

**3. Index.** For each example, check out the parent commit and build two indexes
over its source files: a **sparse** one (BM25, keyword matching) and a **dense**
one (embedding vectors in Postgres/pgvector, meaning matching). Files are cached
by content hash, so the thousands of near-identical checkouts don't get re-embedded
thousands of times.

**4. Retrieve.** Run the query against both indexes and against their fusion,
producing a ranked list of files.

**5. Evaluate.** Compare each ranked list to `gold_files`. Report **top-k
accuracy** (did any correct file make the top k?), **MRR**, and **MAP** — all
defined plainly in `docs/glossary.md`.

---

## What we are comparing

The point of the project is not to build one retriever; it is to establish a
credible baseline and then try to beat it, which is what makes the results
interviewable.

| Method | What it is | Why include it |
| --- | --- | --- |
| **BM25** | Classic keyword ranking; scores a file by how many rare query terms it contains | A strong, un-glamorous baseline. In code retrieval it is often *very* hard to beat, because bug reports name identifiers verbatim |
| **Dense** | Embed query and code into vectors; rank by cosine similarity | Catches paraphrase — "upload fails on big files" matching code about `chunk_size` |
| **Hybrid (RRF)** | Fuse both ranked lists by rank position | The two methods fail differently; combining them usually beats either |
| **+ Cross-encoder rerank** | Re-score the top ~50 candidates with a model that reads query and file *together* | Slow but precise; only affordable on a shortlist |

An honest possible outcome — and one worth stating up front — is that BM25 wins
and the fancy methods do not justify their cost. That is a finding, and reporting
it is more valuable than quietly dropping the comparison.

---

## Evaluation setup

**Split: temporal, per repository, 70/30.** Each repo's fix commits are sorted by
date; the oldest 70% is the **dev set**, the newest 30% is the **held-out eval
set**.

Note that nothing here is *trained* — BM25 and embedding models are used off the
shelf. So "dev set" really means "the set on which we are allowed to tune
hyperparameters": chunk size, the RRF constant, rerank depth, embedding model
choice. The held-out set is touched only once a configuration is frozen.

Why temporal rather than random? Because it matches how the system would actually
be used: you tune on bugs from the past and get judged on bugs from the future.
A random split lets you tune on a 2024 bug and evaluate on a 2019 bug in the same
file, which is optimistic in a way that would not survive deployment. This is
**temporal leakage**, and it is a subtler cousin of the fix-leakage problem above.
Full treatment in `docs/03_evaluation.md`.

## Milestone log

### Milestone 0 — Skeleton & guardrails

Set up the project so that every later milestone has somewhere disciplined to
land. No bug localization happens yet; this is scaffolding, and the point of
doing it first is that a project which is testable and reproducible from commit 1
never has to be retrofitted into being so.

What exists now:

- **Typed configuration** (`config.yaml` + pydantic models). Every setting that
  can change a reported number — filter thresholds, chunk size, split fraction,
  the random seed — lives in one version-controlled file. A result is therefore
  reproducible from (git SHA + config.yaml). The config *rejects unknown keys*
  rather than ignoring them, because a typo'd setting that silently does nothing
  is the easiest way to publish a number produced by settings other than the ones
  you documented.
- **A CLI** (`bugloc`) with every planned command already registered. Commands
  that aren't built yet exit with a pointer to the milestone that will deliver
  them, so `make help` describes the finished system honestly rather than
  growing one command at a time.
- **A Makefile** as the single entry point: `make setup`, `make test`,
  `make mine`, `make eval`.
- **Docker Compose** for Postgres 17 + pgvector, on port 5433 so it cannot
  collide with an existing local Postgres.
- **16 passing tests** covering config loading, override precedence, validation
  of the shipped `config.yaml`, and the CLI surface.

Numbers produced: `16 passed` in 0.26s; `ruff` clean.

### Milestone 1 — History mining → labeled dataset

Built the thing the whole project rests on: a command that turns git history into
labeled bug-localization examples. Full treatment in `docs/01_dataset.md`.

**7,466 labeled examples from 50,490 commits, mined in ~13 seconds.**

| repo | total | dev | held-out | avg gold files |
| --- | ---: | ---: | ---: | ---: |
| flask | 303 | 212 | 91 | 1.38 |
| requests | 398 | 278 | 120 | 1.23 |
| pandas | 6,765 | 4,735 | 2,030 | 1.39 |
| **all** | **7,466** | **5,225** | **2,241** | **1.38** |

77% of examples have exactly one gold file, which means top-1 accuracy is a
meaningful thing to ask for rather than a lottery.

What the milestone added:

- **Mining** via a single `git log --name-only` subprocess per repo (GitPython's
  per-commit diff API would be ~38,000 subprocesses on pandas and take tens of
  minutes; this takes 8 seconds).
- **Seven filters**, each with a logged count, removing merges, non-fixes,
  docs/style commits, mega-commits, docs/test-only commits, and — importantly —
  gold files that don't exist at the parent commit and therefore could never be
  retrieved.
- **Query scrubbing**: literal gold paths removed from 47 queries that named the
  file they fixed.
- **Temporal split**, per repo, 70/30, deterministic.
- **`dataset-stats`** with per-repo breakdowns and an explicit warning when a repo
  is too small to support its own accuracy claim.
- **`samples`**, which prints full examples for hand-review and deliberately
  over-samples borderline cases.
- **66 passing tests**, including one that asserts the buggy code is present at
  `parent_sha` and the fix is not — the project's central correctness property.

**Two findings worth carrying forward.** First, pandas is **90.6% of the held-out
set**, so any aggregate number is essentially a pandas number; flask and requests
contribute 91 and 120 held-out examples, too few to support per-repo claims.
Second, hand-reviewing sampled labels found four real defects (`setup.py` was the
gold label for 108 examples; lowercase `docs:` prefixes bypassed the filter;
squash trailers polluted 357 queries; a leading space defeated every anchored
pattern). Fixing them removed 240 examples — the dataset got smaller and more
trustworthy.
